✓
Idempotency keys weren't idempotent, on either end — double-debit risk
Two-part bug. Backend: whenever a client omitted idempotencyKey, the fallback hashed in a fresh randomUUID() — every retry produced a different key, so the dedup lookup could never match. Replaced with a 2-minute deterministic time bucket, added regression tests. Mobile: the actual client was worse — it generated its idempotency key from DateTime.now() fresh on every submit press, in all three money-moving flows (tip, internal transfer, withdrawal), so its own retries were never stable either. Fixed by capturing the key once per screen instance and reusing it across retries.

✓
Console logo asset — real root cause was route protection, not a broken file
/logo2.png was a perfectly valid file. The actual cause: Next's image optimizer resolves local images via an internal request that carries no cookies at all, and that request was still being caught by the console's auth middleware (nothing on the public-path allowlist covered it) and 307-redirected to /signin — producing an empty, non-image response. Added it to the existing public-exact-paths allowlist, same pattern as /favicon.ico.

✓
Duplicate quest-completion notifications — found the real race condition
The verificationStatus !== 'pending' guard on quest-submission approve/reject ran before the database transaction, not inside it — so two near-simultaneous calls (an admin double-click, or a client retry) could both read "pending", both pass the guard, and both proceed to approve and notify. Replaced with an atomic conditional updateMany inside the transaction on both the approve and reject paths — only one caller can ever actually claim a submission. Added a regression test that simulates the exact race and asserts exactly one notification goes out.
quests/quests.service.ts
✓
Invalid project id no longer crashes with a raw 500
Added NestJS's built-in ParseUUIDPipe to the :id route params — the column really is @db.Uuid (confirmed in schema), so this is the correct, idiomatic fix, not a workaround. Verified locally: a garbage id now returns a clean 400 instead of an unhandled Prisma error. The same unvalidated @Param('id') id: string pattern exists in 15 other controllers — spot-checked 10 of the underlying models and all were UUID-typed too, so this is very likely a safe, valuable broader fix, but each route needs its own quick check before changing it. Flagged as a new item below, not fixed in this pass.
